# План автоматизации тестирования сценария перехода к форме записи и заполнения формы на профессию «Инженер по тестированию» (Netology)

**Стек: Java, Gradle + Selenide + Allure**

План носит **теоретический характер**: описано, *как* автоматизировать сценарии, но **реальные прогоны и отправка форм на действующем сайте не выполняются**.

---

## 1. Перечень автоматизируемых сценариев

Все сценарии делятся на **навигационные** (переход к форме) и **сценарии заполнения формы** (проверка клиентской валидации без фактической отправки заявки).

## 2. Перечень используемых инструментов с обоснованием выбора

| Инструмент | Роль | Обоснование выбора |
|---|---|---|
| **Java 11 +** | Язык программирования | Стандарт индустрии. |
| **Selenide** | Управление браузером | Обёртка над Selenium WebDriver с «умными» ожиданиями из коробки, лаконичный API (`open`, `$`, `$(byText())`), меньше flaky-тестов, отличная интеграция с JUnit 5 и Allure. Идеален для динамического сайта Netology. |
| **JUnit 5** | Тестовый фреймворк | Гибкие аннотации (`@Test`, `@BeforeEach`, `@ParameterizedTest`), параметризация, удобная организация тестов, нативная поддержка в Selenide. |
| **Gradle** | Сборка и управление зависимостями | Декларативное подключение Selenide, JUnit 5, Allure; воспроизводимость окружения, быстрота и лаконичность. |
| **Allure Report** | Отчётность | Наглядные отчёты с шагами (`@Step`), скриншотами при падении (автоматически через Selenide), историей прогонов. Упрощает анализ и демонстрацию. |
| **Page Object Model (POM)** | Архитектура тестов | Разделение локаторов и логики; при изменении вёрстки правится один класс, а не все тесты. |
| **Git + GitHub** | Версионирование и удалённый репозиторий | Возможность совместой работы |
| **GitHub Actions** | CI/CD | Автоматический запуск тестов при пуше; `selenide` умеет запускаться в headless-режиме в CI. |
| **WireMock (опционально)** | Мокирование API | Если понадобится проверять серверную валидацию без реальной отправки — моки изолируют фронтенд от продакшн-бэкенда. |

## 3. Перечень необходимых разрешений, данных и доступов

| Категория | Что необходимо | Пояснение |
|---|---|---|
| **Разрешение на тестирование** | Письменное согласие владельца сайта (Netology) | Сайт реальный; без разрешения автоматические взаимодействия могут нарушать условия использования. |
| **Доступ к тестовому окружению** | URL staging-среды (если есть) | Позволит тестировать форму без риска создания реальных заявок. Если нет — обязательна блокировка POST-запроса на отправку. |
| **Тестовые данные** | Набор фиктивных имён, телефонов, email | Например: `Семён`, `+79770005511`, `test1234@gmail.com`. Не должны принадлежать реальным людям. |
| **Доступ к репозиторию** | Права на создание публичного репозитория на GitHub | Для совместной рабаботы над проектом. |
| **Доступ к CI** | Настройка GitHub Actions | Для автозапуска тестов. |
| **Информация о форме** | Перечень полей, тексты ошибок, правила валидации | Получается ручным исследованием DOM страницы (без сабмита). |

## 4. Перечень и описание возможных рисков при автоматизации

| Риск | Вероятность | Влияние | Меры снижения |
|---|---|---|---|
| **Хрупкость тестов из-за изменения вёрстки** | Высокая | Высокое | Использовать стабильные локаторы (`data-*`, `id`), POM, регулярный рефакторинг. |
| **Flaky-тесты** | Средняя | Среднее | Использовать встроенные ожидания Selenide (`shouldBe(visible)`), избегать `Thread.sleep`, добавлять retry только как крайнюю меру. |
| **Блокировка автоматизации (anti-bot)** | Средняя | Высокое | Согласование с владельцем, запуск в реальном (не headless) браузере при необходимости, эмуляция пользовательского поведения (Selenide позволяет задать user-agent, размеры окна). |
| **Случайная отправка реальной заявки** | Низкая (при мерах) | Критическое | **Обязательная блокировка** POST-запроса на отправку. В Selenide — через прокси/Selenium CDP (`Network.setBlockedURLs`) или перехват через `WebDriver` + `BrowserMobProxy`. Проверять только появление формы. |
| **Зависимость от капчи/сторонних скриптов** | Средняя | Среднее | Тестировать только сценарии без капчи; при наличии — использовать тестовые ключи (если доступны). |
| **Неполнота данных о форме** | Средняя | Среднее | Ручное исследование DOM (без сабмита), анализ селекторов через DevTools, консультация с владельцем. |
| **Проблемы с драйверами браузеров** | Средняя | Среднее | Selenide сам подтягивает драйверы через WebDriverManager; фиксировать версии браузеров в CI. |

## 5. Перечень необходимых специалистов для автоматизации

| Роль | Задачи в проекте |
|---|---|
| **QA-автоматизатор (Java + Selenide) — 1–2 человека** | Написание и поддержка автотестов, настройка Gradle/Maven, POM, интеграция Allure, запуск в CI. |
| **Ручной тестировщик / исследователь — 1 человек (частичная занятость)** | Исследование страницы профессии и формы, сбор точных локаторов, текстов ошибок, правил валидации. |
| **DevOps-инженер — частичная занятость** | Настройка GitHub Actions, стабильное окружение, управление секретами. |
| **Владелец продукта / представитель Netology — согласование** | Выдача разрешения, предоставление тестового окружения (если есть), подтверждение границ допустимого поведения. |

> В рамках учебного проекта достаточно **одного QA-автоматизатора на Java**; остальные роли — по необходимости или в реальном проекте.

## 6. Интервальная оценка с учётом рисков (в часах)

Оценка для одного QA-автоматизатора, владеющего Java + Selenide.

| Этап | Оптимистично | Реалистично | Пессимистично |
|---|---|---|---|
| Исследование страницы и формы (локаторы, тексты ошибок) | 3 | 5 | 8 |
| Настройка проекта (Gradle, зависимости, `.gitignore`, `README.md`, GitHub Actions) | 2 | 4 | 6 |
| Написание Page Objects и хелперов | 4 | 6 | 10 |
| Реализация навигационных сценариев (NAV-01…NAV-04) | 3 | 5 | 8 |
| Реализация сценариев валидации (FORM-01…FORM-13) | 6 | 10 | 16 |
| Настройка блокировки отправки формы (перехват POST через CDP/прокси) | 3 | 5 | 9 |
| Отладка и стабилизация (устранение flaky) | 4 | 8 | 14 |
| Документирование, финальная проверка, пуш в GitHub | 2 | 3 | 5 |
| **Итого** | **27** | **46** | **76** |

**Интервальная оценка:** от **27 до 76 часов**, наиболее вероятно — **40–50 часов**. Пессимистичный сценарий — при отсутствии тестового окружения, необходимости сложного перехвата запросов и частых изменениях вёрстки.
